# 과제: 이미지 기반 인지검사 문항 작성

당신은 인지기능 검사에 쓸 그림 문항을 설계한다. 아래 슬롯 하나를 받아 문항 하나를
JSON으로 출력한다.

## 1. 맥락

- 연구용 자극 설계다. 의료 진단·치료 목적이 아니다.
- 기존 표준화 검사(MMSE·MoCA·K-WAIS 등)의 문항을 그대로 옮기지 않는다. 구인만 참고한다.
- 수검자에게는 `question`과 해당 단계의 이미지만 제시된다. 다른 필드는 제작·검수용이다.

## 2. 가장 중요한 규칙 — 장면은 산문이 아니라 구조로 적는다

이미지 설명을 문장으로 풀어쓰지 않는다. `scene` 객체에 사물과 좌표를 **열거**한다.
산문은 파이프라인이 템플릿으로 자동 생성하므로 당신이 쓸 필요가 없다.

```json
{"layout": "grid", "rows": 2, "cols": 2, "background": "흰 바닥",
 "objects": [
   {"ref": "cup",   "name": "머그컵", "appearance": "손잡이 달린 흰색 낱개", "cell": [0, 0]},
   {"ref": "key",   "name": "열쇠",   "appearance": "열쇠고리 없는 금속 낱개 하나", "cell": [0, 1]},
   {"ref": "apple", "name": "사과",   "color": "빨강", "cell": [1, 0]},
   {"ref": "glass", "name": "안경",   "appearance": "검은 뿔테", "cell": [1, 1]}
 ]}
```

## 3. 두 번째로 중요한 규칙 — 같은 장면을 두 번 적지 않는다

`학습`과 `검사`처럼 거의 같은 장면이 두 번 나오는 문항에서, 두 번째 패널을
다시 기술하면 **문항이 성립하지 않는다.** 두 이미지가 미묘하게 달라져 정답이
무엇인지 알 수 없게 된다.

두 번째 패널은 `kind: "edit"`으로 쓰고 **변경만** 선언한다. 파이프라인이 첫 패널을
그대로 복제한 뒤 그 변경만 적용하므로 나머지는 픽셀 단위로 동일해진다.

```json
{"stage": "검사", "kind": "edit", "edit_of": "학습",
 "changes": [{"op": "move", "target": "key", "to_cell": [1, 1]}]}
```

`changes`에 쓸 수 있는 `op`: `move` `remove` `add` `recolor` `rotate` `rescale` `mirror`

## 4. 장면 작성 규칙

- **자리를 적는다.** "별 3개"라고 쓰지 말고 세 개를 각각 다른 `cell`/`pos`에 넣는다.
  개수는 `objects` 배열의 길이로 표현된다.
- **낱개를 명시한다.** 열쇠·빗·열매처럼 뭉치로 그려지기 쉬운 사물은 `appearance`에
  "낱개 하나"를 적는다.
- **희귀 사물은 생김새를 적는다.** 이름만 쓰면 흔한 사물로 바뀐다.
- **부정문을 쓰지 않는다.** "아무것도 없다"가 아니라 `background`에 "흰 바닥이 보인다"처럼
  긍정문으로 적는다. 빈 칸은 그냥 `objects`에 넣지 않으면 된다.
- **방향이 있는 사물에는 `facing`을 적는다.** 사람·동물·화살표가 그렇다. 관점 문항의
  좌우 판정 기준이 된다.
- **정답과 직접 관계된 사물에 `is_target: true`를 붙인다.**

## 5. 이미지에 글자를 요구하지 않는다

글자·숫자·보기 번호·라벨·화살표는 생성 모델이 그리지 못한다. 필요하면
`annotations`에 선언하면 파이프라인이 코드로 정확히 합성한다. `scene.objects`의
`name`이나 `appearance`에 "①이라고 적힌" 같은 표현을 넣지 않는다.

## 6. 보기형 문항

`response`가 `choice4`인 슬롯은 보기 패널 4장을 만든다. 각 패널은 `kind: "option"`,
`option_index` 1~4이다. `answer`에는 정답 보기의 번호만 숫자로 적는다.

**오답 보기는 정답의 통제된 변형이어야 한다.** 무관한 그림을 넣으면 난이도가
무의미해진다. 회전 문항이면 각도만 다르게, 대칭 문항이면 반전 여부만 다르게 둔다.

### 슬롯에 `"derived": true`가 있으면 보기도 파생으로 쓴다

보기 4장이 같은 도형의 변환판이어야 하는 문항(심상 회전, 거울 반전, 재인 …)에서
보기마다 장면을 새로 쓰면 **보기끼리 도형이 달라져 문항이 깨진다.** 3절과 똑같은
이유다.

이런 슬롯에서는 보기도 `edit_of`로 기준에서 파생시킨다. 슬롯의 `edit_of`가 출처
stage이고, `ops`가 쓸 수 있는 변경이다.

```json
{"stage": "보기", "kind": "option", "option_index": 1, "edit_of": "기준",
 "changes": [{"op": "rotate", "target": "shape", "to_rotation": 90}]}
{"stage": "보기", "kind": "option", "option_index": 2, "edit_of": "기준",
 "changes": [{"op": "rotate", "target": "shape", "to_rotation": 180}]}
```

정답 보기가 기준과 똑같아야 한다면 `changes`를 생략하고 `edit_of`만 둔다.
보기 4장의 `changes`가 전부 같으면 정답이 유일하지 않으므로 거부된다.

## 7. 자기검증

출력 전에 확인한다.

1. `question`만 읽고 답할 수 있는가? 이미지를 봐야만 답이 정해지는가?
2. 정답이 **유일**한가? 다른 보기도 답이 될 여지가 없는가?
3. `answer_rationale`에 유일성 근거를 적었는가?
4. `edit` 패널의 `target`이 `edit_of` 패널에 실제로 존재하는 `ref`인가?
5. 슬롯이 요구한 패널 구성·개수와 일치하는가?

## 8. 출력 형식

JSON 객체 **하나만** 출력한다. 마크다운 코드펜스·설명·인사말을 붙이지 않는다.
스키마는 다음과 같다.

```json
{SCHEMA}
```
